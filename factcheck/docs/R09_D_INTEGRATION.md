## 2. 接口含义与版本兼容

### 2.1 finding 的状态关联

| 配对判断 `status` | `decision` | `evidence_request` | 建议显示文案 |
|---|---|---|---|
| `needs_review` | `ask` | 至少 1 条请求 | “需要补充证据或人工澄清” |
| `confirmed_error` | `proceed` | 空数组 | “本次核查未提出补证请求” |
| `no_issue` | `proceed` | 空数组 | “本次核查未提出补证请求” |

`decision` 是本次核查结果中的处理提示，不是第四种判错状态。`ask` 既可能要求补财报，也可能要求修复输入、核对上下文或裁定来源冲突；不能一律显示成“缺财报”。`proceed` 不代表材料已经通过真人复核、整篇研报正确，或允许自动修改文件。前端收到 `ask` 也不应自动发消息、发起网络检索或重跑模型。

### 2.2 每条请求的 9 个字段

以 `factcheck/src/yjcheck/evidence_requests.py` 的实际输出为准，当前有 **9 个字段**，不是 10 个。D 应保留原值，并将空值或 `unknown` 展示为“待确认/未指定”，不得根据文件名或邻近条目补造内容。

| 字段 | 含义 | 展示要求 |
|---|---|---|
| `doc_role` | `report` 为研报，`source` 为财报/公告 | 显示应补充或核对的材料角色 |
| `field` | 所需业务指标或维度，例如 `revenue`、`period`、`document_integrity` | 显示字段标识；有业务词典时可同时显示中文名称 |
| `period` | 请求所针对的期间 | 按请求本身显示，不能直接复用 claim 的期间；同比的两条请求可能不同 |
| `company` | 公司 | 保留请求中的公司，未知时显示待确认 |
| `basis` | 调整前/后、影响金额、披露值或未知口径 | 展示与指标一起所需的口径 |
| `scope` | 合并/母公司或未知范围 | 与调整口径分开展示 |
| `file` | 可选的相关原文件路径，空字符串表示未指定 | **仅作为文字线索**；不要据此自动读取、打开或下载文件，也不视为已经存在的证据 |
| `request_type` | 请求类型 | 映射下表中文，保留原标识便于核对 |
| `reason` | 具体补充/澄清原因 | 完整展示，不按固定字符数截掉业务含义 |

请求类型中文映射：`provide_source` → 补充来源材料；`repair_input` → 修复或重新核对输入；`clarify_context` → 人工澄清上下文/口径；`resolve_conflict` → 裁定来源冲突。这里的映射用于展示，不改变 C 已生成的请求。

### 2.3 两个统计量

- `summary.evidence_requests`：`decision="ask"` 的 **finding 数量**。
- `summary.evidence_request_items`：所有 ask finding 内请求数组的 **条目总数**。

例如 1 个同比待复核 finding 要求本期和上年同期两个数值，两个统计量分别为 **1 和 2**。它们都不是已确认错误数、待上传文件数、去重后的指标数或人工尚未处理任务数。相同材料被两个 finding 分别请求时，按各 finding 原始条目计数，不跨 finding 去重后替代后端统计。

页面概览和含复核报告必须注明统计来自**本次核查原结果**。人工在 `review.json` 中点击确认或驳回，不自动改写这两个统计量。如以后另做“剩余待处理”指标，必须使用独立名称和独立规则。

### 2.4 历史 1.0.0 与异常数据

1. 新 `1.1.0` 结果应包含每条 finding 的 `decision/evidence_request` 以及 summary 的两个统计量，并满足上述关联。
2. 旧 `1.0.0` 可以没有整组补证字段。此时显示“旧版结果未提供补证信息”，相关计数显示“未提供”，**不能用 `.get(..., [])` 或默认 0 将其解释成无需补证**。原三态、证据、人工复核和导出仍可正常使用。
3. 历史 `1.0.0` 如已有补证字段，按同样的结构及状态关联校验、展示；不能仅因版本号旧就忽略有效请求。**旧代码曾产生“finding 有 decision/evidence_request，summary 只有 evidence_requests、没有 evidence_request_items”的合法历史形态。** 不应将其判为损坏：所有 finding 的请求列表都已提供且校验有效时，可以据其计算条目数，并注明“由已提供请求列表计算”；否则显示“未提供”。这不是将缺失字段默认成 0。读取和导出均保留原 JSON 及 `1.0.0` 版本号，不倒填历史统计。
4. 单个 finding 只出现 `decision/evidence_request` 中的一个、新 `1.1.0` 缺少必需字段、字段类型错误，或出现 `needs_review+proceed`、`ask+空数组`、`proceed+非空数组`，均应提示“补证字段不符合契约”，保留原始结果供排查；不能自行补空值或改状态消除矛盾。已提供的汇总值与完整列表重算不一致时也应显式提示；历史 1.0.0 仅缺新增条目统计不属于此种错误。
5. 保留原错误状态和其他可读内容，让用户知道哪一部分不可用。字段兼容不能以删掉补证数据、生成空清单或默默忽略不一致为代价。

## 3. D 的具体交付

### 3.1 详情与复核视图

在选中 finding 的详情及人工复核区域增加“补充证据 / 人工澄清”区：先显示处理提示，再按数组原顺序逐条显示材料角色、指标/维度、公司、期间、调整口径、合并范围、请求类型、原因及可选文件线索。字段可能不同于当前 claim，特别是同比需要上一年输入时，不能将所有请求都显示成当前年。

保持现有来源证据与补证请求分开展示：`finding.evidence` 是本次判断已经使用的证据；`evidence_request` 是尚需补充或澄清的内容。补证中的 `file` 不是可以直接交给 `highlight_images` 或文件读取函数的可信路径。若用户要查看已经上传的材料，应继续使用已有上传文件与证据定位映射，而不是自动访问请求字符串指定的位置。

本次接入不要求实现自动检索、补证上传闭环或自动重跑。D 应把用户要补什么、为什么补、补哪个期间说清楚。

### 3.2 复核合并导出

| 格式 | 必须保留的内容及验证 |
|---|---|
| CSV | 在原复核列之外增加“补证状态”“补证/澄清条目数”“补充证据清单”；清单包含每条请求的 9 个字段。保持 UTF-8 BOM 及现有公式转义，对新文本列同样执行转义 |
| Markdown | 提供两个汇总计数；各 finding 显示状态、条目数和完整请求内容。正确转义 `\|`、换行及文件文本，避免原因中的竖线破坏表格；长清单可用独立详情段落 |
| PDF | 与 Markdown 一样保留两种计数和逐条请求；按可用宽度换行、按实际高度分页。不能沿用原 PDF 中固定截取字符数的做法裁掉请求，也不能只改 `findings_rows` 而遗漏 `_pdf_lines` 的固定列号 |
| JSON | 维持 `full_json_bytes` 的原结果透传：原 `schema_version`、summary、所有 finding 请求和其他字段保持原值，仅追加独立 `review`。旧版缺失字段仍保持缺失，不人为生成 `proceed` 或空请求 |

以上三种可读格式遇到旧版未提供字段时，输出明确的“旧版未提供”状态，而不是默认 0 条/无需补证。对于旧版已提供完整请求列表、仅缺条目汇总的形态，遵循上节带来源说明的列表计算方式。保留 C 原 JSON/CSV 下载，不用 D 的合并文件覆盖原件。CSV 的每个请求可以在同一单元格内按序号换行；JSON 仍是机器消费完整结构的标准文件。

### 3.3 人工复核记录不覆盖核查原件

继续通过 `ReviewStore` 在同一运行目录的 `review.json` 中保存 finding ID、复核状态、审核人、备注、时间和计时信息。不得修改 `check_result.json`、C `findings.csv`、C `report.md`、C `manifest.json`，也不得根据“采纳系统判断”把 `ask` 改成 `proceed`。人工认为材料已经足够时，先在复核记录中说明；如果后续重新核查，则生成新的运行结果，而不是修改旧运行。

不得把此次 R09 接入写成已实现人工签核制度、完整流程计时验证或自动检索。那些事项另有验收范围。

研报 PDF 解析与知识库开源方案调研报告
面向上市公司研究报告自动核查工具的解析模块选型，兼评 OpenViking 方案
这份调研由负责 PDF 解析模块的同学整理，用于回答两个问题：指导老师提出的 OpenViking 能否把文件解析和知识库一起解决；以及有哪些开源项目可以借鉴，支撑文本与表格提取、页码与坐标保留、解析失败识别这三项硬需求。结论写在最前面，后面依次给出 OpenViking 的能力边界、同类开源项目的对比、建议的模块架构，以及解析失败的判定方法。文中所有项目的星标数、许可证和功能描述均以 2026 年 9 月 24 日的仓库实际情况为准。
一、结论摘要
OpenViking 的定位决定了它只能承担一半。OpenViking 值得参考，但它解决的是知识库与检索这一半，不能替代高精度的版面解析。它把 PDF 转成 Markdown 之后再做目录化与向量化，页码只以 HTML 注释的形式留在中间稿里，块级坐标完全不留存，而研报核查最看重的恰恰是“这句结论来自第几页的哪个位置”。如果用它同时承担解析，证据回溯能力会直接缺失。
• 解析层：建议用专门的版面解析引擎做主干，首选 MinerU 或 Docling，两者都能输出带页码和边界框（bbox）的结构化结果。
• 知识库层：OpenViking 或 RAGFlow 都可以承担检索与多文档横向对比，两者与解析层用一份统一的页级、块级 JSON 契约解耦。
• 失败识别：用“规则质量分 + 双引擎交叉校验 + VLM 抽检”三层机制，并在数据契约里把 page 与 bbox 设为必填字段，缺失即判定失败。
• 许可证：OpenViking 为 AGPL-3.0，如后续产品化需评估开源义务；MinerU 为 Apache-2.0 附加商业与署名条款；Docling 为 MIT，最宽松。
这套分工的好处是团队可以并行推进：解析同学先把“可回溯的中间表示”做扎实，知识库同学在同一份 JSON 之上做检索与横向比对，任何一方换实现都不影响对方。
二、OpenViking 是什么
OpenViking 是字节跳动火山引擎团队开源的、面向 AI Agent 的上下文数据库。它的官方描述是“Self-evolving Context Database for AI Agents”，目标是把知识库检索、Agent 记忆和技能统一到一套文件系统里。项目 2026 年 1 月创建，到 9 月 24 日已有约 3.86 万星标、3000 余个分支，当天仍有代码提交，属于热度很高的活跃项目。

2.1 它的核心抽象
• 虚拟文件系统：所有上下文以 viking:// 协议组织成目录树，可以用 ls、tree、read、grep 这类文件操作浏览，资源、记忆、技能各占一类目录。
• 三层上下文：L0 一句话摘要、L1 目录概览、L2 原始正文，Agent 先读摘要判断相关性，再决定是否展开全文，用来压低检索的 token 消耗。
• 目录级检索：语义检索可以限定在某个项目或知识子树上执行，而不是在一整片扁平向量池里盲搜。
• 上下文编译：可以把素材组织成 wiki、知识图谱或报告，这是它宣传里最接近“多文件横向对比”的能力。
• 学术支撑：配套论文覆盖记忆管理（VLDB 2026）、目录感知检索（ICDE）与结构化文档的检索增强生成。
从产品成熟度看，OpenViking 的工程完成度不低：有独立的文档站、Studio 演示站、Railway 一键部署、以及 Claude Code、Codex、Cursor、Trae 等 Agent 的接入插件。单作为知识库选型，它是当下最有竞争力的选项之一。
三、用 OpenViking 做 PDF 解析的实际能力
这一节的结论来自直接读它的源码与官方文档，而不是只看宣传页。它的 PDF 处理实现位于仓库的 openviking/parse/parsers/pdf.py，整体路线是先把 PDF 转成 Markdown，再交给 MarkdownParser 建目录树。

3.2 页码与坐标的实际处理
• 页码：仅以 HTML 注释形式写入中间 Markdown，形如 <!-- Page 12 -->，表格则是 <!-- Page 12 Table 1 -->。
• 表格：用 Markdown 表格语法输出，没有单元格坐标，也没有跨页合并、表头续接等结构信息。
• 坐标：仅在提取图片时使用过页面 bbox，用于裁剪图片区域，解析结果的正文与表格都不保留边界框。
• 文档模型：解析结果的数据结构 ResourceNode 只有 root / section 两级节点加 Markdown 正文，没有块级字段，无法承载坐标。
• 扫描件：走视觉大模型的页面理解，输出摘要、概览、全文和标题四类字段，同样不含坐标。
• 元数据：只记录总页数、已处理页数、抽取表格数、图片数这类计数，没有任何逐页质量分或置信度。
另外两点需要知道：Office、EPUB 等格式走 AnyDoc 转换器，但源码中对 PDF 明确抛出不支持、要求改用 PDFParser；更高质量的解析需要开启 Understanding API，那是火山引擎的商业服务，不是开源部分。

4.2 底层库与专用模型
• pdfplumber 与 PyMuPDF：直接读取 PDF 文本层，能拿到字符级坐标与页码，速度极快，适合做前置探测、文本层判断与交叉校验基线。
• Camelot 与 Table Transformer：分别面向规则表格与深度学习表格检测，可用作表格抽取的补充手段。
• PaddleOCR-VL 与 DeepSeek-OCR 等视觉语言模型：面向扫描件与图片型研报，输出 Markdown 或 JSON，坐标粒度弱于 PP-StructureV3。
• OmniDocBench（opendatalab）：文档解析评测基准，覆盖研报、论文、教材等场景，标注含多边形定位、页码、阅读顺序与表格结构。
综合判断：如果要在两周内跑通一条可用流水线，MinerU 与 Docling 是性价比最高的两个主干选择。MinerU 中文场景与表格效果更好、开箱工具链更全；Docling 的数据模型最干净，页码、坐标、字符跨度三件套齐全，许可证也最宽松。PP-StructureV3 适合作为表格与扫描件的增强组件。

六、建议的模块架构
把解析与知识库解耦，用一份规范化的中间表示做接口。解析层负责把任何格式的研报变成统一 JSON，知识库层只消费这份 JSON，不再接触原始 PDF。这样解析引擎可以随评测结论替换，知识库也可以独立演进。

6.1 建议的中间表示字段
每个解析单元都必须带页码和边界框，这是可回溯的下限。建议字段如下，其中 page 与 bbox 设为必填，缺失即视为解析失败。

七、解析失败的识别方法
解析失败通常不会抛出异常，而是安静地输出乱码、漏页或错行的结果，因此需要主动检查。建议按“确定性规则、交叉校验、模型抽检”三层组织，逐层提高成本，也逐层提高召回。
7.1 第一层：确定性的完整性检查
• 字段完整性：每个块必须有页码与边界框，表格必须行列数一致，缺失或越界直接判失败。
• 页数与覆盖率：比对 PDF 页数与解析页数；统计每页字符密度，出现空页或字符密度异常低的页要标记。
• 乱码检测：统计替换字符、CID 编码残留、私用区字符的比例，电子版研报里这个指标最灵敏。
• 结构合理性：阅读顺序是否与坐标顺序一致，标题层级是否出现异常跳变，表格列数在同一张表内是否突变。
• 数值合理性：抽查金额、百分比、单位字段，判断千分位、负号、括号负数是否被错误解析。
7.2 第二层：双引擎交叉校验
同一页用两套机制解析，比对结果的一致性。实践中最省成本的组合是“版面引擎 + 原生文本层”：主引擎用 MinerU 或 Docling，对照引擎用 PyMuPDF 直接读文本层。两者归一化后计算文本相似度，再单独比对数字序列。文本层缺失说明是扫描件，需要改走 OCR 分支；两者差异过大说明版面识别可能出错，该页进入人工复核队列。这也顺带解决了电子版与扫描件的路由问题。
7.3 第三层：视觉模型抽检
按比例随机抽取页面，渲染成图片后让视觉模型判断“图中内容与解析文本是否一致”，重点检查表格与数字。抽检比例控制在 5% 到 10% 即可，既能发现系统性错误，又不会让成本失控。视觉模型抽查出的问题页，应回流成测试样本，用于验证规则阈值是否合理。
7.4 输出与闭环
每页给出一个质量分和状态（正常、警告、失败），附上具体原因，汇总成解析质量报告。核查环节的结论只允许引用“正常”与“警告”页的证据；“失败”页只提示解析异常，不进入自动结论，避免把解析错误传播成业务误判。这样处理还有一个额外好处：评审可以清楚看到系统知道自己哪里不确定。
八、评测与验收指标
建议自建一个小而真实的数据集：30 到 50 篇研报，覆盖电子版、扫描版、双栏、跨页大表、图片型图表、页眉页脚干扰这几类情况，每篇人工标注少量关键结论与关键财务数据的页码与位置，作为金标准。

• OpenViking：AGPL-3.0，通过网络提供服务时需履行开源义务，比赛演示阶段无影响，产品化前需评估。
• MinerU：Apache-2.0 附加条款，月活超过一亿或月收入超过两千万美元需单独商业许可，在线服务需显著标注来源。
• Marker 与 Surya：代码为 Apache-2.0，模型权重为 OpenRAIL-M，商用前需确认模型条款。
• Docling、PaddleOCR、RAGFlow、olmOCR、Unstructured、pdfplumber、Camelot：MIT 或 Apache-2.0，限制最少。
如果团队考虑长期做成产品，优先选择 MIT 与 Apache-2.0 的组合：解析用 Docling 或 PaddleOCR，知识库用 RAGFlow，法律负担最小。OpenViking 更适合作为设计思路参考，或先用它验证检索与对比效果。

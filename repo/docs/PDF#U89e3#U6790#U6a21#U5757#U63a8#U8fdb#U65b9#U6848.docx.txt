PDF 解析模块推进方案
对齐竞赛交付要求的工作主线、交付物清单与时间安排
竞赛规则里有三条直接压在解析模块身上：运行环境封闭或半封闭且全过程留痕，交付与展示版本一致的完整源码和依赖，第三方成果必须逐项登记来源、版本与许可证。这意味着解析模块不能停在“能跑出结果”这一步，必须同时满足可核验、可追溯、可复现。这份方案把要求翻译成具体的交付物和检查点，并给出三周的推进顺序，供组会和答辩使用。
一、推进主线
先定契约与合规，再写流水线，最后打包。下一步不是先写解析代码，而是先定契约和合规边界，再做流水线，最后统一打包。顺序颠倒会把返工集中在最后一周，而交付物本身是评分项，不能靠临时拼凑。
• 第一优先：把数据契约定下来。页码与坐标是必填字段，还要加上引擎、版本、参数、模型哈希这些溯源信息。
• 第二优先：把链路全本地化。任何把研报发给外部接口的做法都不符合封闭环境要求，包括商业解析服务和在线模型接口。
• 第三优先：把留痕做成机制。文件访问、工具调用、计算过程、结果生成四类记录在流水线里自动产生，而不是事后补写。
• 第四优先：把交付物当成产品。源码、依赖、运行说明、第三方清单、评测报告，缺一项就是一个失分点。

另外，作品设计要求里的“区分事实、推论与观点”和解析直接相关：解析结果属于事实层，必须能精确指回原文位置；模型对内容的判断属于推论层，要单独标注，不能混在解析文本里。解析模块的定位可以概括为：为后端的核查与推理提供带位置、带质量标记的证据原料。

四、可追溯的数据契约
这是整个模块的核心交付物，建议直接写成 JSON Schema 并用数据类做校验。字段设计围绕两件事：能不能指回原文，以及能不能复现这一次解析。
{  "run_id": "20260924T1030Z_7f3a91",  "doc": {"doc_id": "600XXX_2025H1",          "source_path": "data/raw/600XXX_2025H1.pdf",          "sha256": "...", "total_pages": 42},  "engine": {"name": "mineru", "version": "4.0.2",             "strategy": "advanced", "model": "MinerU2.5-VLM",             "model_sha256": "...", "params": {"lang": "ch"},             "started_at": "2026-09-24T10:30:12+08:00",             "duration_s": 18.4},  "pages": [    {"page": 12, "page_size": [595.0, 842.0], "status": "ok",     "quality": {"text_coverage": 0.94, "garbled_ratio": 0.0007,                 "engine_agreement": 0.97},     "blocks": [       {"block_id": "p12_b3", "type": "text", "order": 3,        "bbox": [72.0, 310.5, 523.0, 402.8],        "text": "公司 2025 年上半年营业收入同比增长 18.6%..."},       {"block_id": "p12_t1", "type": "table",        "bbox": [72.0, 430.0, 523.0, 690.0],        "caption": "表 3 主要财务指标", "source_note": "公司半年报",        "cells": [{"row": 0, "col": 0, "text": "指标",                    "bbox": [72.0, 430.0, 180.0, 452.0]}]}     ]}  ],  "quality_report": {"status": "warn", "failed_pages": [17],                     "reasons": {"17": ["text_coverage=0.21"]}}}
• run_id：一次解析的唯一编号，日志、产物、报告共用，是追溯的索引键。
• engine 区块：引擎名、版本、档位、模型名与权重哈希、参数、起始时间与耗时，复现时需要逐项对齐。
• page_size 与 bbox：单位为点（1/72 英寸），原点在页面左上角，与 pdfplumber 的口径一致；前端高亮按渲染缩放比换算。
• status 与 quality：失败识别的载体，页级给出状态与三项指标，块级默认继承页面状态。
• source_note：保留研报里标注的数据来源，核查时可以区分原始出处与分析结论，呼应事实与推论的区分要求。

九、需要确认的问题
下面五个问题会直接改变技术路线，建议在下次组会上一次问清。
• 现场网络条件：比赛现场是否提供外网，是否要求完全离线运行。这决定权重必须提前离线打包还是可以现场下载。
• 算力规格：现场机器是否配备图形处理器、显存多大。这决定本地视觉模型能否上，以及解析档位怎么选。
• 模型要求口径：是否强制使用国产模型、是否允许调用云端接口。这影响引擎选择与第三方登记方式。
• 最终交付形态：是分析报告、系统演示还是两者都要，是否需要现场点击回溯原文位置。这决定坐标高亮做到什么程度。
• 许可证尺度：评审对 AGPL 组件的态度，是否需要把链路控制在 MIT 与 Apache 许可范围内。
十、现场演示与答辩要点
• 最有说服力的一段演示，是当众展示解析失败被系统识别出来的过程：同页渲染图、主引擎输出、对照引擎输出、质量分与判定原因并列呈现。
• 第二条演示线索是从核查结论回跳到原文位置，点击结论直接高亮到具体页面的具体区块，这直接回应证据支撑充分性。
• 答辩时主动区分层次：解析输出是事实层，模型判断是推论层，失败页不进入自动结论，体现风险审慎。
• 主动说明第三方边界：哪些是开源组件、版本是多少、用在哪里、哪些是自研，比被动回答更安全。
• 准备好复现演示：现场执行同一条解析命令与校验命令，证明展示版本与提交源码一致。
